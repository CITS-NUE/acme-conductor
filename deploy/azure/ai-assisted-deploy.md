# 生成 AI を使った Azure への導入ガイド

Azure への導入（[`walkthrough.md`](walkthrough.md)）には数十のコマンドがある．
加えて，権限・命名・ID の判断があちこちに挟まる．すべて人手で行うのは
現実的ではない．一方で，すべてを AI に任せるのは危険である．この文書では
Claude Code のようなコーディングエージェントを使う前提で，次の 4 点を
まとめる．

- 誰が何を担うか
- どんな指示を出すか
- AI にどのパラメタを仮に決めさせるか
- AI が実際に何をするか

実際に staging 環境を立ち上げたときのやりとりがもとになっている．

## 基本方針: 決めるのは人，調べて書くのは AI，実行は人と AI で分ける

| 種類 | 担当 | 例 |
|---|---|---|
| **決める** | 人 | 命名，環境（staging か本番か），対象ホスト，誰に管理権限を与えるか |
| **調べる**（読み取り） | AI | 既存リソースの一覧，権限の確認，ログの読み取り，リポジトリのドキュメントとコードの参照 |
| **書く**（ローカル） | AI | パラメタファイル，Runner 設定，Entra 用スクリプト，手順書，issue や PR の文面 |
| **確認する** | 人 | AI が出した案・スクリプト・`what-if` の差分を読んで承認する |
| **実行する**（クラウドへの書き込み） | 人（または承認後に AI） | RG や Key Vault の作成，アプリ登録，デプロイ，権限の有効化（PIM） |

最後の行が重要である．エージェントの安全機構（Claude Code の auto mode の
判定など）は，共有リソースの変更や権限の付与を AI 自身が実行することを
**止める** ことがある．それで正しい．その場合は，AI が用意したコマンドを人が
実行し，出力を AI に返す．Claude Code では入力欄で `!` を先頭に付けると，
そのコマンドの出力が会話に取り込まれる．

## 始める前に

- **環境**: `az login` 済みの Azure CLI，`gh`（issue や PR を扱う場合），
  リポジトリのクローン．`jq` と `openssl` もあるとよい．
- **権限**: [walkthrough の「役割と必要な権限」](walkthrough.md#役割と必要な権限)
  を参照．PIM のロールは期限付きなので，AI が必要だと言った時点で有効化すれば
  よい．
- **秘密情報の扱い**: 署名用の秘密鍵，トークン，組織の ID をチャットや公開
  issue に貼らない．AI には「秘密鍵はリポジトリの外に `chmod 600` で置く」
  「組織固有の値のファイルは `.git/info/exclude` に入れる」「公開 issue には
  ID を書かない」と最初に伝える（後述のルール例）．

## パラメタシート（AI に渡す仮設定）

最初に次のシートを埋めて渡すと，確認の往復が減る．わからない欄は空欄でよい．
その場合 AI は既存リソースを調べて案を出す．**命名に関わる欄は，空欄でも
AI に勝手に決めさせない**．案を出させ，人が確定する．

```markdown
## デプロイ用パラメタシート
- 環境: staging（CA は Let's Encrypt staging）
- サブスクリプション: DNS ゾーンと同じもの（<名前>）
- リソースグループ: rg-acme-staging（japaneast，新規）
- namePrefix: acme-stg
- roleNamePrefix: ACME Conductor Staging
- Key Vault: 新規 kv-acme-stg-<org>（RBAC）
- DNS ゾーン: <チャレンジ用ゾーン> / <その RG>（既存．変更しない）
- 最初の target: <CNAME 委任済みの 1 ホスト>
- バインディング名: acme=letsencrypt-staging / dns=azure-dns-<zone> / store=keyvault-staging
- ACME の連絡先: <組織の窓口アドレス>
- OIDC: Entra ID．アプリ登録 acme-conductor-api / acme-conductor-gui，ロール ACME.Admin / ACME.Viewer，principalClaim=oid
- ingress: external=true，許可 CIDR=[]（わかれば学内の送信元）
- migration: 初回は {}（registry）
- その他: テンプレートの既定値のまま
```

実際には，このシートを表（項目・案・理由）の形で用意して画像で渡しても
十分に通じた．

## フェーズごとの指示と，AI がすること

各フェーズを「指示の例」「AI が実際にすること」「人が確認すること」の
3 つで示す．指示は短くてよい．**「確認すべきこと」を指示に含める** のがこつである．

### フェーズ 1: 着手と現状把握

> 最新の main を pull してから，Azure へのデプロイを進めてください．ただし，命名パラメタは事前に私に確認すること．

AI がすること（すべて読み取り）:

- `git pull`，`deploy/azure/README.md` と `main.bicepparam` を読む．
- 既存リソースを一覧する（`az group list`，`az network dns zone list`，`az keyvault list`，`az containerapp job list`）．
- 既存の証明書基盤（`cert-infra` など）の Job の環境変数を読み，ゾーン，Key Vault，連絡先，対象ホストを把握する．
- 命名の候補をいくつか選択肢として示し，質問する．

人が確認すること: AI が見つけた既存資源の理解が正しいか．ここで
パラメタシートを渡す．

### フェーズ 2: パラメタの確定

> パラメタ類はこちらを参照．ただし組織の略称は <新> に読み替えて．（パラメタシートを添付）

AI がすること:

- シートと既存リソースを突き合わせる．Key Vault 名が空いているか確認する（`checkNameAvailability`）．
- シートにない値に案を出す．例: `allowedDnsSuffixes` を target そのものに絞る．
- シートの記述に抜けがあれば質問する（例: 「アプリ登録名は下記」とあるのに，その下記が添付されていない）．

人が確認すること: **シートにない値を AI が補ったところ**．AI は「cert-infra と
同じにしておく」といった善意の補完をする．その補完が
製品の制約に反していることがある（[つまずき例](#ai-がつまずいた例)）．

### フェーズ 3: 権限の確認

> 必要な権限が足りているか確認して．足りないものは何をどこで有効化すればよいか教えて．

AI がすること（読み取り）:

- 実効権限（`Microsoft.Authorization/permissions`）を取得する．
- 有効な割り当てと条件（`roleAssignmentScheduleInstances`）を取得する．
- PIM で有効化できるロール（`roleEligibilityScheduleInstances`）を取得する．
- Entra のディレクトリロールと，一般ユーザーがアプリを作れるかを確認する．
- 不足を表にする．例: 「`roleDefinitions/write` がない → PIM の `User Access Administrator`」「アプリ作成不可 → `Application Administrator`」．

人が確認すること: PIM の有効化は **人がポータルで** 行う．AI には「有効化した」と伝える．

### フェーズ 4: ローカルの準備

AI がすること:

- 署名鍵ペアを生成する（`acme-* keygen`．なければ OpenSSL）．保存先は `~/.acme-conductor/<env>/`（700/600）．
- `<env>.runner-config.json` と `<env>.bicepparam` を書き，`.git/info/exclude` に追加する．
- `az bicep build-params` でコンパイルが通ることを確認する．

人が確認すること: ファイルがリポジトリの外，またはコミット対象外にあるか．

### フェーズ 5: クラウドへの書き込み（RG，Key Vault，アプリ登録）

> 続けて．（または）スクリプトを見せてから実行して．

AI がすること:

- 作成コマンド（`az group create`，`az keyvault create`）と Entra 用のスクリプトを **書いて見せる**．スクリプトの形は [walkthrough の手順 5](walkthrough.md#5-entra-id-のアプリ登録) を参照．
- 実行が安全機構に止められたら，無理に回避せず，人に実行を頼む．
- 人が実行した結果（`oidcAudience=…` など）を受け取り，パラメタファイルに反映する．アプリ登録の中身を読み取りで検証する．

人が確認すること: スクリプトの中身．特に，**シートの仕様にない追加**（今回は
「割り当てが必要」をオンにする設定）を AI が明記しているか．

### フェーズ 6: what-if

AI がすること: 秘密鍵を環境変数に読み込み，`az deployment group what-if` を
実行して差分を要約する．要約に含める点は次のとおり．

- 新規作成の数
- 計算不能（Unsupported）の項目とその理由
- **既存の本番リソースへの変更の有無**

人が確認すること: 既存の本番 RG への変更が想定どおりか（今回は DNS
ゾーンへのロール割り当て 1 つだけ）．

### フェーズ 7: デプロイ

AI がすること: デプロイコマンドを用意する．人が実行し，出力を返す．

失敗した場合は，AI に **切り分けを計画させる**．手を動かす前に，仮説と検証手順，
それぞれの結果が何を意味するかを示させる．今回の例を示す:

> 3 で．なんか cert-infra のときにも同じような問題にあたった気がするので，そっちの実装もみてみて

AI がしたこと:

- 姉妹リポジトリの記録（ABAC 条件付き委任の扱い）を読んだ．
- 仮説を立てた．1 つ目は「割り当てるカスタムロールがまだ存在しない」．
- 副作用の小さい順に試した．
  1. ロール定義だけを先に作って再試行した → 仮説は外れた．
  2. 自分自身への一時的な割り当てを直接作成してすぐ削除した → 直接の割り当ては通る．
  3. `--validation-level Template` で再試行した → 成功．
- 結論: 事前検証が条件を評価できないことが原因（[#34](https://github.com/CITS-NUE/acme-conductor/issues/34)）．

**副作用のある検証**（上の 2 など）は，AI が提案し，人が選んでから行う．

### フェーズ 8: デプロイ後の確認

> （デプロイ成功の出力を貼る）

AI がすること（読み取り）:

- `/healthz`・`/readyz`・トークンなしの API の HTTP ステータスを確認する．
- ロール割り当ての内容を確認する．
- Runner の実行一覧と，その実行ログを読む．

今回はここで，Runner が毎分 `Failed` になっていることを AI が見つけた．
ログから原因（予約済みの環境変数）を特定し，設定を直して再デプロイを依頼した．
**デプロイが成功しても，Runner の最初の実行を見るまで完了とみなさない**
ように指示しておくとよい．

人が行うこと: GUI のリダイレクト URI の登録（AI が用意したコマンドを実行）．

### フェーズ 9: 発行テスト

人が行う: GUI に `ACME.Admin` でサインインし，ポリシーと target を登録する．

AI がすること: run の状態，Runner のログ，Key Vault の証明書，TXT レコードの
後始末を読み取りで確認する．

### フェーズ 10: 振り返りと還元

> 権限の話は issue へ，環境変数については PR をお願いします．あと，今回実行したコマンド群をもとに手引きの MD が欲しいです．

AI がすること:

- つまずきを分類する．製品やドキュメントの不足は issue か PR に，組織固有の事情はローカルのメモに分ける．
- 公開リポジトリには ID を伏せて書く．
- 実行したコマンドを手順書にまとめる（[`walkthrough.md`](walkthrough.md)）．
- 次回のためにメモを残す（どのファイルに何があるか，毎回必要なオプション）．

## AI に最初に伝えておくルール（例）

リポジトリの `CLAUDE.md` やユーザー設定に書いておくと，毎回言わずに済む．

```markdown
- 命名に関わるパラメタ（RG，namePrefix，roleNamePrefix，Key Vault，バインディング名，アプリ登録名）は確定前に必ず確認する．
- クラウドへの書き込み（作成・変更・削除・権限付与）は，コマンドを提示して承認を得てから．止められたら回避せず人に実行を頼む．
- 署名用の秘密鍵はリポジトリ外に 600 で置き，チャットや出力に内容を出さない．
- 組織固有の値のファイル（<env>.bicepparam，<env>.runner-config.json）はコミットしない（.git/info/exclude）．
- 公開 issue や PR にはサブスクリプション ID・テナント ID・オブジェクト ID・UPN を書かない．
- デプロイ前に what-if の要約（新規作成，変更，削除，既存の本番リソースへの影響）を示す．
- デプロイ後は Runner の最初の実行ログまで確認して完了とする．
- テンプレートや製品の制約を知らずに値を補わない．補うときはその値と根拠を明示する．
```

## AI がつまずいた例

| 事例 | 何が起きたか | 教訓 |
|---|---|---|
| 善意の補完 | cert-infra に合わせて Runner 設定に `LEGO_DISABLE_CNAME_SUPPORT=false` を足した．予約済みの変数で，Runner が毎分失敗した | AI が補った値は明示させ，製品のドキュメント（`docs/runner.md`）と照合させる |
| 権限の読み違い | 条件付きの権限を「条件上は許可されるはず」と判断したが，事前検証では通らなかった | 仮説と検証を分けて進めさせる．副作用のない順に試させる |
| 抜けた情報 | シートに「アプリ登録は下記」とあったが，その部分が添付されていなかった | AI が推測で埋めず質問したのが正解だった．人も添付を確認する |
| 言葉の食い違い | 「本番デプロイ」と依頼したが，シートは staging の構成だった | 構成はシートが優先．食い違いは AI に指摘させる |
