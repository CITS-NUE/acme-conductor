# 0015: 署名付きジョブエンベロープと Result エンベロープとリプレイ台帳

- ステータス: 採択
- 日付: 2026-09-22

## 背景

Phase 4 までは，Conductor と Runner の間の唯一のトランスポートは，Conductor が
書き自身の子プロセスが読む run ごとの非公開ディレクトリであった．Container Apps
ランチャー（[ADR 0014](0014-azure-container-apps-job-launcher.md)）はジョブを
他のプリンシパルが書けるファイル共有越しに引き渡し，プラットフォームは同じ
execution の引数を 2 回提示し得る．脅威モデルはまさにこれを見込んでいた．
すなわち `JobSpec` を包む署名付き・期限付きのエンベロープ（T2，転送中の改竄），
nonce，そして再実行に対する Runner 側の確認（T3，リプレイ）である．決めるべき
だったのは，その構成，鍵をどこに置くか，run レジストリにアクセスできない Runner
がリプレイをどう扱うか，そして Conductor が秘密鍵を持つことが「Conductor は
決してシークレットに触れない」（[ADR 0005](0005-conductor-never-touches-secrets.md)）
とどう整合するか，である．

## 決定

- **JWS 構成，Ed25519 のみ．** `SignedCertificateReconcileJob` は `protected`
  （base64url の JSON ヘッダ: `alg` は `EdDSA` に固定，`kid`，`issuedAt`，
  `expiresAt`，`nonce`），`payload`（シリアライズされたままの JobSpec バイト列の
  base64url），`signature`（`protected || "." || payload` に対する Ed25519 署名，
  RFC 7515/8037）を運ぶ．正規化なし，アルゴリズム交渉なし，文書内に鍵素材なし．
  署名されたバイト列がそのまま検証され，その後厳格にデコードされる．ヘッダは
  他のあらゆる文書と同様に厳格な JSON オブジェクトであり（未知のメンバーは
  拒否されるので，`jku` 風のポインタを紛れ込ませることはできない），エンベロープ
  全体は独自の JSON Schema とフィクスチャを持つ．
- **非対称鍵．秘密鍵は Runner に対する Conductor の ID である．** Conductor は
  1 つの Ed25519 秘密鍵を持つ（`jobSigning.privateKeyFile`．`acme-conductor keygen`
  で生成，PKCS #8 PEM，起動時に 1 度読む）．Runner が持つのは公開鍵だけである
  （`jobSigning.publicKeys`．ローテーション中は複数）．したがって侵害された Runner
  は他の Runner 向けのジョブを偽造できない．HMAC ならそれが可能だったであろう．
  この鍵は DNS・Store・クラウドの資格情報ではなく，「Runner が本物とみなすジョブ
  を生成する」以外の何も解錠しない．それこそが Conductor の役目である．ADR 0005
  の規則はデータプレーンの資産についてのものであり，そのまま成り立つ．鍵識別子は
  両側で導出される（`kid` = 生の公開鍵に対する SHA-256 の先頭 16 桁の 16 進）ので，
  手作業で合意すべきものは何もない．
- **署名するかどうかは設定で 1 度だけ決まる．** すべてのランチャーは
  `launcher.JobDocument` を通じてジョブをシリアライズする．署名者が設定されて
  いればエンベロープ，そうでなければ素の JobSpec である．ローカルランチャーは
  どちらでも動いてよい．Container Apps ランチャーは署名者なしに存在することを
  拒否し，Conductor の設定は `jobSigning` のないそのバインディングを拒否する．
- **Runner は切り替えのどちら側でもフェイルクローズする．** `jobSigning` が
  設定されていればエンベロープしか受け付けない．素の JobSpec は `InvalidJobSpec`
  である．設定されていなければ，エンベロープも同様に `InvalidJobSpec` である
  （Runner にできるのは署名を無視することだけで，それはしない）．検証は認可の前，
  どのバインディングが解決されるよりも前に行われる．取り出された JobSpec は
  その後これまでとまったく同じように検証・認可される．**署名は誰が文書を
  生成したかを証明するのであって，それに従って行動すべきことを証明するのでは
  ない．** それを決めるのは依然として信頼された認可ポリシーである．
- **有効期間は Runner の時計で判断する．** `expiresAt` は厳格で，`issuedAt` は
  `clockSkewSeconds`（5 分）まで未来にあってよい．Conductor の `validitySeconds`
  （既定 15 分）はプラットフォームの開始遅延を覆えばよい．Runner は何かをする
  前にこの期間を確認するからである．コントラクトは有効期間の上限を 24 時間と
  する．
- **リプレイ台帳は Runner の状態ディレクトリに置く．** Runner は run レジストリ
  にアクセスできないので，独自の台帳を持つ．`stateDir/jobs.d/<runId>` のマーカー
  ファイルを，処理を始める前にアドバイザリロック（`stateDir/.jobs.lock`）の下で
  排他的に作成し，それぞれにエンベロープの有効期限を保持する．有効期間内に
  同じ run が 2 度目に提示されれば `InvalidJobSpec`（「already executed」）で
  ある．マーカーはそのエンベロープがどのみち検証を通らなくなった時点（有効期限
  にスキューを加えたもの）で刈り取られるので，台帳の大きさは有効期間あたりの
  run 数で抑えられる．`stateDir` を共有する Runner は台帳も共有する．nonce は
  同一の spec であってもすべてのエンベロープを一意にする．台帳が run をキーと
  するのは，2 度実行してはならないのが run だからである．
- **ID は拒否されても保たれる．** run の ID は検証の前に payload から覗き見る
  ので，検証に失敗したエンベロープでもその run を指す `failed` の Result が
  得られ，Conductor は結果不明ではなく拒否を記録する．
- **Result は逆方向に署名される．** 共有トランスポートは両方向に書き込み可能で
  あり，Result は Conductor が永続化し判断の根拠とする値（`expiresAt`，
  `fingerprintSha256`，`storeObjectRef`）を運ぶ．`runId`，`targetId`，もっともらしい
  status を保ったまま共有に書き込む者は，さもなければそれらを書き換えられる．
  そこで Runner は独自の Ed25519 鍵（`resultSigning.privateKeyFile`．
  `acme-runner keygen` で生成）を持ち，すべての Result を
  `SignedCertificateReconcileResult` で包む．同じ JWS 構成，同じ厳格なヘッダ，
  Result の正確なバイト列を payload とする．Runner の公開鍵
  （`resultSigning.publicKeys`）を設定された Conductor はそれ以外を受け付けない．
  検証は Result が信頼された鍵を持つ Runner から来たことを証明する．ランチャーは
  依然として，それが差し出した run を指しプラットフォームの判定と一致することを
  確認する．こちら側にリプレイ台帳は不要である．run id は一意であり，別の run の
  Result はその確認によって拒否される．ジョブと同様，切り替えは両方向でフェイル
  クローズである．署名するよう指示された Runner は鍵を読み込めないときに未署名の
  成功を報告しない（run は失敗する）．claim モードの Runner は Result 署名鍵なしに
  ジョブをまったく取らず，`resultSigning` を持つ Conductor は素の Result を
  Result なしとして扱う．Container Apps ランチャーは両方の鍵を要求する．ローカル
  ランチャーはどちらか一方，どちらもなし，両方のいずれでも動いてよい．2 種類の
  エンベロープは 1 つの構成を共有し，署名はヘッダと payload を覆い，外側の `kind`
  は覆わない．ジョブエンベロープが Result エンベロープとして読まれるのを防いで
  いるのは，両側が互いに素な鍵集合を信頼していることと，payload が異なる厳格な
  スキーマでデコードされることである．したがって **1 つの鍵ペアを両方向に決して
  使ってはならない**．

## 検討した代替案

- **共有シークレットによる HMAC．** 却下．すべての Runner が他のすべての Runner
  向けのジョブを偽造できる鍵を持つことになり，Conductor は ADR 0005 の意味での
  データプレーンのシークレットを持つことになる．
- **プラットフォームのトークン（Conductor の ID に発行された Entra トークンを，
  Runner がテナントの鍵に対して検証する）．** Phase 4 では却下．コントラクトを
  1 つのクラウドに縛り，Runner 内で署名鍵のネットワーク取得が必要になり，
  ローカルランチャーでは動かない．
- **JobSpec 内部のフィールドレベルの署名**（文書の種類を 1 つに保つ）．却下．
  署名のための正規化されたシリアライズが必要になり，正規化こそ署名方式が
  間違いを犯す場所である．正確なバイト列を包めばそれを完全に避け，JobSpec は
  変わらないままである．
- **run レジストリに対する Runner 側のリプレイ確認．** Runner に Conductor の
  データベースへの経路を与えなければ不可能であり，それはアーキテクチャが
  禁じている．台帳は重要な期間について同じ保証を与える．

## 結果

- 転送中のジョブの改竄（FQDN の変更，バインディングのすり替え，有効期限の延長）
  は，何かが解決・発行される前に検出され `InvalidJobSpec` として報告される．
  リプレイされたジョブは `lego` の起動前に拒否される．トランスポート上で改変・
  すり替えられた Result は Conductor に拒否され，記録されるのではなく run が
  失敗する．これら 3 つはこれまで脅威モデルで「保証されない」であった．
- 署名は，侵害された Conductor が不正なジョブに正当に署名すること（T1）には
  対処しないし，できない．それを制限するのは依然として Runner の信頼された
  ポリシーである．
- 操作者はさらに 2 つのシークレットを所有する．Conductor のためだけにマウント
  されるジョブ署名の秘密鍵と，Runner のためだけにマウントされる Result 署名の
  秘密鍵である．ローテーションは検証側で追加的に行う（そちらに新しい公開鍵を
  加え，署名者を切り替え，古い鍵を取り除く）．
- 侵害された Runner はあらゆる Result に署名できる．以前もあらゆる Result を
  書けたのと同じである．Result の署名が対処するのは共有トランスポートへの他の
  書き込み者（T2）であり，侵害された Runner ではない．その到達範囲は Runner
  自身の狭い権限が制限する．
- 台帳は `stateDir` ボリューム上にある．その `flock` にはアカウント状態のもの
  と同じネットワークファイルシステムの注意事項がある．
- Runner は 128 KiB までのジョブファイルを読む（64 KiB の JobSpec のエンベロー
  プ）．JobSpec 自体の上限は変わらない．
