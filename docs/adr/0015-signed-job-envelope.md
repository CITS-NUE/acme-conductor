# 0015: Signed job envelope and replay ledger

- Status: Accepted
- Date: 2026-09-22

## Context

Until Phase 4 the only transport between the Conductor and a Runner was a
private per-run directory written by the Conductor and read by its own
child process. The Container Apps launcher ([ADR 0014](0014-azure-container-apps-job-launcher.md))
hands the job over a file share that other principals can write, and a
platform can present the same execution arguments twice. The threat
model planned for exactly this: a signed, expiring envelope around the
`JobSpec` (T2, tampering in transit) with a nonce and a Runner-side
check against re-execution (T3, replay). What had to be decided is the
construction, where the keys live, what a Runner does about replay
without access to the run registry, and how the Conductor's holding a
private key squares with "the Conductor never touches secrets"
([ADR 0005](0005-conductor-never-touches-secrets.md)).

## Decision

- **JWS construction, Ed25519 only.** A `SignedCertificateReconcileJob`
  carries `protected` (base64url JSON header: `alg` fixed to `EdDSA`,
  `kid`, `issuedAt`, `expiresAt`, `nonce`), `payload` (base64url of the
  JobSpec bytes exactly as serialized) and `signature` (Ed25519 over
  `protected || "." || payload`, RFC 7515/8037). No canonicalization,
  no algorithm negotiation, no key material in the document: the bytes
  that were signed are the bytes verified and then strictly decoded. The
  header is a strict JSON object like every other document (unknown
  members rejected, so a `jku`-style pointer cannot be smuggled in), and
  the whole envelope has its own JSON Schema and fixtures.
- **Asymmetric keys; the private key is the Conductor's identity
  towards Runners.** The Conductor holds one Ed25519 private key
  (`jobSigning.privateKeyFile`, generated by `acme-conductor keygen`,
  PKCS #8 PEM, read once at start). Runners hold public keys only
  (`jobSigning.publicKeys`, several during a rotation). A compromised
  Runner therefore cannot forge jobs for other Runners, which an HMAC
  would have allowed. The key is not a DNS, Store or cloud credential
  and it unlocks nothing but "produce a job Runners will consider
  authentic", which is what the Conductor is for; ADR 0005's rule is
  about the assets of the data plane and stands. Key identifiers are
  derived on both sides (`kid` = first 16 hex characters of SHA-256 over
  the raw public key), so nothing has to be agreed by hand.
- **Signing is decided by configuration, once.** Every launcher
  serializes the job through `launcher.JobDocument`: an envelope when a
  signer is configured, a bare JobSpec otherwise. The local launcher may
  run either way; the Container Apps launcher refuses to exist without a
  signer, and the Conductor configuration refuses that binding without
  `jobSigning`.
- **The Runner fails closed on both sides of the switch.** With
  `jobSigning` configured it accepts only envelopes: a bare JobSpec is
  `InvalidJobSpec`. Without it, an envelope is `InvalidJobSpec` too (the
  Runner could only ignore the signature, and would not). Verification
  happens before authorization and before any binding is resolved; the
  unwrapped JobSpec is then validated and authorized exactly as before —
  **signing proves who produced a document, not that it should be
  acted upon**; the trusted authorization policy still decides that.
- **Validity window on the Runner's clock.** `expiresAt` is strict;
  `issuedAt` may lie up to `clockSkewSeconds` (5 minutes) in the future.
  The Conductor's `validitySeconds` (15 minutes by default) only has to
  cover the platform's start latency, because the Runner checks the
  window before it does anything; the contract caps validity at 24
  hours.
- **Replay ledger in the Runner's state directory.** The Runner has no
  access to the run registry, so it keeps its own: `stateDir/jobs.d/<runId>`
  marker files, created exclusively under an advisory lock
  (`stateDir/.jobs.lock`) before any work starts, each holding the
  envelope's expiry. A second presentation of a run within its window
  is `InvalidJobSpec` ("already executed"); markers are pruned once
  their envelope could no longer verify anyway (expiry plus skew), so
  the ledger is bounded by the runs per validity window. Runners sharing
  a `stateDir` share the ledger. The nonce makes every envelope unique
  even for identical specs; the ledger is keyed by run because a run is
  what must not execute twice.
- **Identity survives rejection.** The run identity is peeked from the
  payload before verification, so an envelope that fails verification
  still yields a `failed` Result naming its run, and the Conductor
  records the rejection rather than an unknown outcome.

## Alternatives considered

- **HMAC with a shared secret.** Rejected: every Runner would hold the
  key that forges jobs for every other Runner, and the Conductor would
  hold a data-plane secret in the ADR 0005 sense.
- **Platform tokens (an Entra token issued to the Conductor's identity,
  verified by the Runner against the tenant's keys).** Rejected for
  Phase 4: it ties the contract to one cloud, needs a network fetch of
  signing keys in the Runner, and does not work with the local launcher.
- **A field-level signature inside the JobSpec** (keeping one document
  kind). Rejected: it needs a canonical serialization to sign, and
  canonicalization is where signature schemes go wrong; wrapping the
  exact bytes avoids it entirely and leaves the JobSpec unchanged.
- **Runner-side replay check against the run registry.** Not possible
  without giving the Runner a path into the Conductor's database, which
  the architecture forbids; the ledger gives the same guarantee for the
  window that matters.

## Consequences

- Tampering with a job in transit (a changed FQDN, a swapped binding, an
  extended expiry) is detected and reported as `InvalidJobSpec` before
  anything is resolved or issued; a replayed job is refused before
  `lego` starts. Both were "not guaranteed" in the threat model until
  now.
- Signing does not, and cannot, address a compromised Conductor
  legitimately signing a bad job (T1); the Runner's trusted policy still
  bounds that.
- Operators own one more secret: the signing private key, mounted for
  the Conductor only. Rotation is additive (add the public key to the
  Runners, switch the Conductor, remove the old key).
- The ledger lives on the `stateDir` volume; its `flock` has the same
  network-filesystem caveat as the account state's.
- The Runner reads job files up to 128 KiB (an envelope of a 64 KiB
  JobSpec); the JobSpec limit itself is unchanged.
