既存環境からの移行

すでに IaC（Infrastructure as Code）でホスト一覧を管理し，別の仕組みで 証明書を更新している場合，切替日を設けずに ACME Conductor へ移せます． 一覧を取り込み，しばらくの間は発行させずに既存の仕組みと突き合わせて見比べ， 準備ができてから切り替え，必要ならフラグ 1 つで元に戻せます．

このページは，学内の IaC（Bicep など）でホスト一覧を管理し，別の仕組みで 証明書を更新している組織を想定しています．著者らの環境では，この既存の 仕組みを「cert-infra」（固定ホスト一覧を lego で更新し Key Vault に取り込む，Bicep 定義の Container Apps Job）と 呼んでいます．ACME Conductor は cert-infra リポジトリ自体を 変更しません．読むだけで，止めるのも操作者です．詳しくは docs/migration.md と ADR 0020 を参照してください．

移行するものとしないもの

移行するのは管理対象の名前の集合（FQDN）だけです．一覧が 寄与するのは FQDN のみであり，それ以外は何も寄与しません．

移行するもの

  • ホスト名（FQDN）の一覧のみ．Conductor の target レジストリに， FQDN ごとに 1 つの Target として作成されます．

移行しないもの

  • ACME アカウント — Runner の lego は 自身の状態ディレクトリの下に新しいアカウントを登録します．両方の アカウントは CA 側で共存できます．
  • 証明書 — 切替後の初回実行で，取り込んだ各 target に 新しい証明書が発行され，Conductor 自身のオブジェクト名の下に格納 されます．既存の仕組みが使っていた名前ではありません．
  • ポリシー — 許可するサフィックス，使う ACME バインディング，更新のタイミングは，一覧からは導出されません． 管理者が「取り込みプロファイル」の中で一度だけ決めます．

target source フラグ

設定 migration.targetSource が，どちらのシステムが証明書を 発行するかを決めます．3 つのモードがあり，起動時に設定として読まれます （API からは変更できません）．変更は設定変更と再起動だけで完結し，データの 移動や再計算は起きません．

比較のカテゴリ

比較は一覧を読み，API と同じ方法ですべての名前を正規化し（小文字化，末尾の ドット 1 つの除去，構文検査），各名前を 1 つのカテゴリに振り分けます． 不正な項目が 1 つでもあれば，一覧全体の読み込みが失敗します．

カテゴリ意味取り込みが行うこと
added一覧にあり，レジストリにない．プロファイルから target を作成する．
changed両方にあるが，レジストリの target が無効化されているか，プロファイルと異なるポリシーまたはバインディングを名指している．何もしない．操作者が判断する．レポートはどのフィールドが異なるかを示す．
missingレジストリにあり，一覧にない．何もしない．移行は何も削除しない（ADR 0008）．不要なら target を無効化すること．
unchanged両方にあり，同じ．何もしない．
rejected一覧にあるが，プロファイルのポリシーがその名前を許可しない（サフィックスまたはワイルドカードの規則）．何もせず，他の何も行わない．一覧全体が，修正されるまで一切取り込まれない．

所有者は比較の対象ではありません．一覧は所有者を知らず，取り込み後に操作者が target ごとにプロファイルの所有者を精緻化することは十分にありえます． 取り込みは冪等で，既定では dry-run です．何かを作成するには API では dryRun: false を，CLI では --apply を渡します．

一覧のソース

一覧は次のいずれか 1 つから読みます．

Bicep パラメータファイル

bicepParamFile（parameter 併用可，既定は targetDomains）．既存の IaC 管理のホスト一覧（例えば infra/main.bicepparam）をそのまま読みます．専用のリーダが param <name> = [ … ] 文，コメント，単純な文字列リテラルを 理解し，評価が必要になるもの（補間文字列，変数，関数呼び出し）はすべて 拒否します．評価が必要な一覧は，先に TargetList へ書き出してください．

TargetList 文書

jsonFile．厳密にデコードされる汎用の JSON 文書 （deploy/examples/targets.example.json）で， 特定の IaC 形式に依存しません．acme-conductor migrate list --bicepparam FILE --output json で書き出せるほか，他組織では 独自のスクリプトで直接生成しても構いません． 

{
  "apiVersion": "acme-conductor.cits-nue.github.io/v1alpha1",
  "kind": "TargetList",
  "fqdns": [
    "leaf.cerdad.example.ac.jp",
    "www.example.ac.jp"
  ]
}

インライン一覧

fqdns．設定そのものに書いた名前の配列（最大 10000 個）． Container Apps デプロイはこの方法で一覧を得ます．

ソースはサーバ側の設定 migration.source です．CLI はファイルを ローカルで読んで名前を送ることもできるので，操作者の手元に既存の IaC の チェックアウトがあれば足ります．どのソースであっても，寄与するのは FQDN だけで，取り込まれた target のポリシーやバインディングは常に migration.profile から来ます．一覧がバインディングを選ぶことは 決してできません．

設定例

deploy/examples/conductor-config.migration.example.json の migration セクション抜粋です． 

"migration": {
  "targetSource": "shadow",
  "source": {
    "bicepParamFile": "/srv/cert-infra/infra/main.bicepparam",
    "parameter": "targetDomains"
  },
  "profile": {
    "policyRef": "cert-infra",
    "executionBinding": "local",
    "dnsBinding": "azure-dns-staging",
    "storeBinding": "filesystem-dev",
    "owner": "cert-infra migration"
  },
  "compareIntervalSeconds": 300
}

手順

以下は，既存の仕組みで管理されたデプロイ（または，1 台のホストでのリハーサル） から ACME Conductor へ移す手順です．前提として，Runner が既存の仕組みと 同じ DNS ゾーンでチャレンジを完了でき，証明書ストアに書き込めることが必要です．

  1. 暗転状態で始める． targetSource: shadow（または iac），既存の IaC の一覧を指す migration.source，そして移行対象ホストのために 作った migration.profile（allowedDnsSuffixes が ホストを覆い，acmeBinding はリハーサルが終わるまでステージング CA を指す）で Conductor をデプロイします．既存の仕組みのジョブは更新を 続けます．この時点で Conductor は，証明書を発行せず，DNS レコードを変更せず， クラウドリソースに一切触れません．
  2. 差分を見る． 
    acme-conductor migrate diff --bicepparam ~/src/cert-infra/infra/main.bicepparam \
  --server https://acme-conductor.example.ac.jp --token-file token
    すべての名前が added に入り，rejected には 何もないことを期待します．rejected の名前があれば，取り込む前に ポリシー（または一覧）を修正します．
  3. 取り込み，そして適用する． 同じコマンドを import で実行すると，--apply が 何を作成するかを示す dry-run になります．--apply を付けると 実際に作成し，監査ログに各 target を target.imported として 記録します．もう一度実行しても何も作成されません（冪等）．
  4. shadow で様子を見る． 既存の一覧がまだ変わりうる間は targetSource: shadow のままに しておきます．GUI の Migration ページ（と GET /migration）が 最新の比較を示し，結果が変わるたびに migration.compared 監査イベントが記録されます．この間もレジストリは完全に編集可能で，何も 発行せずにポリシー・所有者・バインディングを準備できます．
  5. 切り替える． targetSource: registry を設定して再起動します．スケジューラは 取り込んだ target（一度も reconcile されていない）に run を計画し，Runner が 発行・格納し，各 target に証明書の概要が現れます．
  6. 利用側を向け直す． 証明書ストアのオブジェクトを名前で参照している利用側（例えば Application Gateway のリスナー）を，新しくできたオブジェクトへ操作者が向け直します． これが移行の中で利用側から見える唯一の手順であり，このリポジトリの外に あります．古いオブジェクトは手で削除されるまで残ります．
  7. 既存の仕組みを止める． 操作者が選んだタイミングで既存のジョブを止めます（スケジュールの一時停止， またはデプロイの削除）．両者は別々の ACME アカウントと別々のオブジェクト名を 使うため，一時的に重なっていても構いませんが，その代償として CA の レート制限に対してホストごとに 1 回余分な発行が生じます．

ロールバックは targetSource: iac （または shadow）を設定して再起動するだけです．Conductor は 直ちに計画を止め，進行中の run は通常どおり完了するかシャットダウン時に キャンセルされ，レジストリは shadow フェーズと切替が記録したすべてを 保持します．既存の仕組みのジョブを止めていたなら再開します．復元すべき データはなく，何も削除されていません．

切替のタイムライン

CLI と API

CLI（acme-conductor migrate）は既定で dry-runで， --apply を渡さない限り target を作成しません．changed の target を更新することも，missing の target を削除することも 決してありません．

コマンド目的
acme-conductor migrate list (--bicepparam FILE [--parameter NAME] | --json FILE) [--output text|json]ソースを読み，正規化済みの名前を印字する．サーバ不要．
acme-conductor migrate diff [SOURCE] [--server URL] [--token-file FILE] [--output text|json]レジストリと比較してレポートを表示する．
acme-conductor migrate import [SOURCE] [--server URL] [--token-file FILE] [--apply] [--output text|json]取り込む．--apply なしは dry-run．
メソッドとパス目的
GET /api/v1alpha1/migrationフラグ，発行が有効かどうか，設定されたソースとプロファイル，shadow では最新の比較．
GET /api/v1alpha1/migration/diff設定された一覧を比較する → レポート．viewer が読める．
POST /api/v1alpha1/migration/diff{"fqdns": […]} を比較する → レポート．
POST /api/v1alpha1/migration/import{"fqdns": […], "dryRun": true} を取り込む．dryRun の既定は true．何かを作成したときはスケジューラを起こす．

テストは本物の ACME 認証局やクラウド API を決して呼びません．比較と取り込みは 本物の SQLite レジストリに対して実行され，acme-conductor migrate 自体も動作中の Conductor に対してエンドツーエンドで検証されています．詳しくは docs/migration.md を参照してください．
